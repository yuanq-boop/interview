## 1. What labs and vendors publish about harness iteration loops, with quantitative harness-only gains

### Takeaway
By 2025–2026 every major lab and coding-agent vendor described the same loop: run the agent on realistic tasks, read traces, attribute failures to the harness (prompt, tools, context, verification, workflow), make targeted changes, re-run on held-out or regression sets. Harness-only changes regularly move benchmarks by 5–15 points with a fixed model (LangChain +13.7 pts on Terminal-Bench 2.0; Cognition +12% on internal evals; Factory's harness #1 on Terminal-Bench), and harness/infra choices alone can exceed the gaps between frontier models.

### Cited Findings

**Anthropic**
- "Building effective agents" (Dec 19, 2024): recommends starting with the simplest solution (direct API calls, workflows) and only adding agentic complexity when it demonstrably helps; introduces "agent-computer interface (ACI)" design. For their SWE-bench agent they report spending more time optimizing tools than the overall prompt, e.g. switching tools to require absolute file paths after the model made mistakes with relative paths, after which "the model used this method flawlessly." [prior knowledge] — [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- "Writing effective tools for agents — with agents" (Sep 11, 2025): four-step loop: (1) prototype tools as a local MCP server/DXT and test in Claude Code, feeding API docs (e.g., llms.txt); (2) generate realistic eval tasks ("Strong evaluation tasks might require multiple tool calls—potentially dozens"), each paired with a verifiable outcome, run with a simple agentic loop, asking the agent to output reasoning and feedback before tool calls; (3) analyze transcripts and metrics (redundant calls → adjust pagination; invalid-parameter errors → unclear descriptions); (4) paste transcripts into Claude Code and let it refactor tools and descriptions, checking held-out test sets for overfitting. — [Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Same post: metrics tracked = top-level accuracy, runtime per tool call and task, total tool calls, total tokens, tool errors. Claude-optimized Slack and Asana MCP servers beat human-written ones on held-out sets (numbers given only in charts). A `response_format` concise vs detailed enum cut a response from 206 to 72 tokens (~1/3). Claude Code caps tool responses at 25,000 tokens by default. Claude Sonnet 3.5 reached SOTA on SWE-bench Verified after tool-description refinements. Design principles: consolidate multi-step tools, namespace by service/resource, return natural-language identifiers, paginate/filter/truncate with sensible defaults, write actionable error messages, unambiguous parameter names (`user_id` not `user`). — [Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "Effective context engineering for AI agents" (Sep 29, 2025): context engineering = managing everything that enters the context at inference, not just the prompt. System prompts at "the right altitude" (between brittle hardcoded logic and vague guidance). Minimal, non-overlapping tool sets ("if a human engineer can't definitively say which tool should be used…an AI agent can't be expected to do better"). Iteration recipe: "start by testing a minimal prompt with the best model available," then add instructions/examples for observed failure modes. Techniques: just-in-time retrieval via lightweight identifiers, compaction (tune for recall first, then precision), structured note-taking outside context, sub-agents returning distilled summaries, tool-result clearing as "one of the safest lightest touch forms of compaction." — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Effective harnesses for long-running agents" (Nov 26, 2025): failure-driven design with Opus 4.5 in the Claude Agent SDK. Observed failures → fixes: (a) agent tries to one-shot everything and runs out of context → initializer agent writes a JSON feature list (200+ features, all `"passes": false`), one feature per session; (b) later sessions declare victory prematurely → feature list + progress file; (c) buggy/undocumented state left behind → git commits + `claude-progress.txt`, each session starts with `pwd`, git log, progress file, `init.sh`, and a basic end-to-end test; (d) features marked done after only unit tests/curl → Puppeteer MCP browser testing "dramatically improved performance." JSON chosen over Markdown because the model was less likely to inappropriately overwrite it; prompt says "It is unacceptable to remove or edit tests." No benchmark numbers reported. — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- "Demystifying evals for AI agents" (Jan 9, 2026): start with "20-50 simple tasks drawn from real failures"; read transcripts across many trials to separate agent failures from grader bugs. Example: Opus 4.5 initially scored 42% on CORE-Bench due to grading bugs and ambiguous specs, rising to 95% after fixes. Distinguishes capability evals (low pass rate, "hill to climb") from regression evals (near 100%); capability evals "graduate" into regression suites; run evals on each agent change and each model upgrade in CI/CD; use pass@k vs pass^k (75% per-trial → ~42% pass^3). Customer examples: Descript (moved from manual grading to LLM graders with human calibration; separate quality and regression suites), Bolt (built in ~3 months: static analysis + browser agents + LLM judges). — [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Infrastructure noise: Anthropic found infrastructure configuration alone can shift agentic coding scores by more than typical leaderboard gaps between top models; on Terminal-Bench 2.0 a 3x resource ceiling cut infra error rates from 5.8% to 2.1% (p < 0.001) while the score lift stayed within noise (p = 0.40). A secondary write-up reports a 6-point gap between strict and uncapped containers for the same model+harness. — [ZenML summary of Anthropic infra-noise post](https://www.zenml.io/llmops-database/infrastructure-noise-in-agentic-coding-evaluations) (secondary; original not fetched)
- Agent Skills (Oct 16, 2025): folders with SKILL.md + scripts/resources loaded via progressive disclosure (name/description in context; body loaded on demand) as a way to extend harness behavior without bloating context; Anthropic advises building skills by watching where Claude struggles and iterating, and having Claude itself capture successful approaches into skills. [prior knowledge] — [Anthropic, Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Claude Agent SDK (renamed from Claude Code SDK, Sep 29, 2025) packages the Claude Code harness (agent loop, tools, compaction, subagents, hooks) for reuse; Anthropic frames the agent loop as "gather context → take action → verify work → repeat." [prior knowledge] — [Anthropic, Building agents with the Claude Agent SDK](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

[prior knowledge] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

### Inferences
- The consistent harness levers are: (1) tool interface/descriptions and response shape, (2) verification/feedback loops (tests, browsers, self-check before finishing), (3) context management (compaction, notes/progress files, sub-agents, tool-result clearing), (4) guardrail middleware (time budgets, loop detection), (5) repository-level legibility (short AGENTS.md as index, docs, linters).
- Harness tuning is model-specific: LangChain (Opus untuned → lower), Cognition (rebuilt for Sonnet 4.5), Cursor (per-model tool names) all show a harness optimized for one model does not transfer automatically, which implies harness iteration must be rerun at each model upgrade.
- Reported harness gains (3–14 pts) are of the same order as run-to-run and infra noise (3.4 pts spread; 6 pts from container caps), so single-run leaderboard comparisons of harnesses are weak evidence.

## 2. Trace-driven error analysis and LLM-assisted failure clustering / fix proposal

### Takeaway
The practitioner consensus (Husain & Shankar) is: humans read ~100 traces and do open coding → axial coding into a failure taxonomy → count → build targeted evals; LLMs can help cluster/label after humans have coded 30–50 traces, but should not replace initial open coding. Labs and LangChain push further, using agents to analyze transcripts in parallel and propose harness/tool edits, with humans reviewing changes and held-out sets guarding against overfitting.

### Cited Findings
- Husain/Shankar method: randomly sample ~100 traces; read each until the first snag and write a free-form note (open coding, borrowed from qualitative research); group notes into a failure taxonomy (axial coding, "the most important step") and count per category; iterate until new traces stop revealing new failure modes ("theoretical saturation"); write evals only for the failure modes found, using LLM-as-judge for subjective ones. — [Hamel Husain, Evals FAQ: why is error analysis so important](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html); [Alex Strick van Linschoten course notes (May 23, 2025)](https://alexstrick.com/posts/2025-05-23-error-analysis-to-find-failure-modes.html); [Lenny's Newsletter](https://www.lennysnewsletter.com/p/building-eval-systems-that-improve)
- On automation: LLMs can help with first-pass grouping after you have coded ~30–50 traces yourself, but initial open coding should be done by reading raw traces; "never skip this or delegate it." — [Hamel Husain, What parts of evals can be automated with LLMs?](https://hamel.dev/blog/posts/evals-faq/what-parts-of-evals-can-be-automated-with-llms.html) (via search summary)
- Atla's experiments on automating error analysis: step-by-step span-level annotations with open-ended critiques gave the highest human agreement and LLM-judge alignment. — [Atla, What works when automating error analysis](https://atla-ai.com/post/automating-error-analysis)
- Shankar et al. "Who Validates the Validators?" (EvalGen, 2024): criteria drift—users' evaluation criteria change as they grade outputs, so judge criteria must be co-developed with human grading. [prior knowledge] — [arXiv 2404.12272](https://arxiv.org/abs/2404.12272)
- LLM-driven variant (LangChain): parallel error-analysis agents over LangSmith traces, main agent synthesizes, then targeted harness changes. — [LangChain blog](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)
- "Agents improving their own tools" (Anthropic): agents output reasoning/feedback before each tool call; transcripts concatenated and given to Claude Code to rewrite tool implementations and descriptions; held-out test sets check overfitting; Anthropic notes much of the post's advice itself came from this process. — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Grader/task bugs are a major class of "failures" discovered only by reading transcripts (CORE-Bench 42% → 95% after fixing grading/specs). — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### Inferences
- A practical division of labor emerges: humans own open coding, taxonomy definition, and accept/reject of changes; LLMs own scale (summarizing, clustering, tagging thousands of traces, drafting fixes); held-out evals own the final verdict.
- The first step in any failure investigation should be "is it the agent, the grader, or the infrastructure?" since all three show up in traces.

### Gaps
- No public quantitative comparison found of LLM-clustered vs human-coded taxonomies on agent (multi-step) traces specifically.

## 3. Tooling: observability, eval harnesses, optimizer integrations

### Takeaway
Tracing platforms (LangSmith, Braintrust, Arize, W&B Weave, Langfuse) all added LLM-assisted trace analysis (clustering, natural-language debugging assistants) and some prompt optimizers by 2025–2026, while Harbor and Inspect AI became the common harnesses for running agent benchmarks in sandboxes. Commentators note none fully closes the loop from production trace → tracked issue → auto-generated eval → continuous regression testing.

### Cited Findings
- LangSmith: Insights (LLM-based clustering of traces into categories, insights agent prioritizing by frequency/impact), Polly AI assistant for natural-language trace debugging; LangSmith CLI and Agent Skills (trace, dataset, evaluator) so coding agents can query/export traces. — [Latitude comparison](https://latitude.so/blog/best-llm-observability-tools-agents-latitude-vs-langfuse-langsmith) (vendor-affiliated); [LangSmith CLI & Skills](https://www.langchain.com/blog/langsmith-cli-skills); [LangSmith skills docs](https://docs.langchain.com/langsmith/skills)
- Braintrust: "Loop" AI assistant drafts scorers from natural-language goals, builds eval datasets from logs, turns production failures into eval cases, and optimizes prompts inside Braintrust; "Topics" (beta) ML-based failure clustering. — [Latitude](https://latitude.so/blog/best-ai-agent-observability-tools-2026-comparison); [Braintrust agent observability guide](https://www.braintrust.dev/articles/agent-observability-complete-guide-2026)
- Arize: open-source Phoenix lacks a prompt optimizer; commercial Arize AX has a meta-prompt optimizer + Prompt Hub; licensing of Phoenix described as Elastic License 2.0 (sources disagree whether that counts as "open source"). — [Latitude](https://latitude.so/blog/langsmith-alternatives-for-ai-agents); [MLflow top-5 observability tools](https://mlflow.org/top-5-agent-observability-tools/)
- Overall gap claim: no vendor fully closes production trace → tracked issue → auto eval → regression testing. — [Latitude](https://latitude.so/blog/best-llm-observability-tools-agents-latitude-vs-langfuse-langsmith) (vendor with own product to sell; treat as opinion)
- Harbor: framework used to orchestrate Terminal-Bench 2.0 runs in sandboxes (Daytona in LangChain's case), handling verification and scoring. — [LangChain blog](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)
- Inspect AI (UK AI Security Institute, open source) is a widely used eval framework for agentic tasks with sandboxed tools. [prior knowledge] — [Inspect AI](https://inspect.aisi.org.uk/)
- GEPA reflective prompt optimizer adopted in practitioner tooling: integrations listed include the OpenAI Cookbook; optimizes "any text parameter — prompts, code, agent architectures, configurations." — [gepa-ai/gepa](https://github.com/gepa-ai/gepa); [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/partners/self_evolving_agents/autonomous_agent_retraining)

### Inferences
- The tooling trend is to expose traces to coding agents (CLIs, skills, MCP) so the improvement loop itself is agent-driven, rather than only offering dashboards for humans.
- Prompt optimizers in these platforms mostly target single prompts; whole-harness changes (tools, middleware, workflow) are still made by engineers/coding agents editing code.

### Gaps
- W&B Weave's specific optimizer/clustering features were not verified in this session.
- Most tool comparisons found are vendor-authored; independent evaluations of these features are scarce.

## 4. "Harness engineering" / "context engineering" consensus best practices; automated harness search in production

### Takeaway
2025 popularized "context engineering" (Karpathy/Tobi Lütke framing; Anthropic, Manus, LangChain posts) and Feb 2026 popularized "harness engineering" (OpenAI). Consensus: start minimal; keep a small stable entry point (short AGENTS.md/system prompt) with progressive disclosure (docs, skills); few well-designed tools; externalize state to files/git; build verification into the loop; enforce invariants mechanically (linters, tests, hooks/middleware) instead of prose; re-tune per model. Automated harness search in production is limited to prompt-level optimization (GEPA/metaprompt loops) and agent-proposed changes reviewed by humans; no lab reports fully autonomous production harness search.

### Cited Findings
- Start minimal, add instructions per failure mode; right-altitude prompts; minimal tools; JIT retrieval; compaction; notes; sub-agents. — [Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Short AGENTS.md as map, structured docs, mechanical enforcement of "golden principles," doc-gardening agents, agent-legible observability (Chrome DevTools, logs). — [OpenAI, Harness engineering](https://openai.com/index/harness-engineering) via [ignorance.ai](https://www.ignorance.ai/p/the-emerging-harness-engineering) and [SWEQuiz](https://www.swequiz.com/articles/openai-harness-engineering)
- Progressive disclosure via Agent Skills. [prior knowledge] — [Anthropic, Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Middleware/hook-based guardrails (time budget, loop detection) as harness components alongside prompts, tools, skills, sub-agents, memory. — [LangChain blog](https://blog.langchain.com/improving-deep-agents-with-harness-engineering)
- KV-cache-aware context design, file-system memory, recitation, keep errors in context. [prior knowledge] — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- "Model-harness fit": the harness must be shaped around a specific model's trained behaviors. — [Nicolas Bustamante, Model-Harness-Fit](https://nicolasbustamante.com/blog/model-harness-fit); [Cursor via yage.ai](https://yage.ai/share/cursor-agent-harness-evaluation-first-en-20260501.html)
- Practitioner guides/awesome lists consolidating harness engineering in 2026. — [awesome-agent-harness](https://github.com/AutoJunjie/awesome-agent-harness); [Vitthal Mirji, Build the harness, not the code (Feb 2026)](https://vitthalmirji.com/2026/02/build-the-harness-not-the-code-a-staff/principal-engineers-guide-to-ai-agent-systems/); [Orchestra guide](https://www.getorchestra.io/guides/agent-harness-engineering)
- Automated prompt-level optimization loops published by OpenAI (metaprompt agent + 4 graders; GEPA) with explicit rollback caveat. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/partners/self_evolving_agents/autonomous_agent_retraining)
- Semi-automated: Anthropic's Claude-rewrites-tools loop and LangChain's trace-analyzer skill both keep a human choosing which changes to merge and validating on held-out sets. — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents); [LangChain](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)

### Inferences
- The field shifted from "write a better prompt" (2023–24) to "engineer the environment the model works in" (2025–26): repo docs, tools, verifiers, middleware, memory files. Prose instructions are increasingly replaced by mechanical enforcement because models ignore or overwrite prose (cf. Anthropic choosing JSON over Markdown).
- Fully automated whole-harness search (ADAS/DGM-style) does not appear in any production write-up found; the adopted pattern is "agent proposes, human disposes, evals verify."

### Gaps
- No primary source found reporting a fully automated harness search running in production at a lab or vendor.
- Google's published harness-iteration practices (Gemini CLI, Jules, ADK) not located in this session.

## 5. Cost/time budgets, stopping criteria, versioning and regression testing

### Takeaway
Few practitioners publish dollar/time budgets for improvement loops. What is reported: small seed eval sets (20–50 tasks; ~100 traces for error analysis), stop error analysis at saturation, stop capability work when an eval saturates (graduate to regression), and gate every harness/model change on regression suites plus online metrics; prompt/harness versions must be rollback-able. Noise (3–6 pts) means multiple runs are needed before accepting a change.

### Cited Findings
- Seed size: 20–50 tasks from real failures. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Error-analysis budget and stop rule: ~100 traces; continue until no new failure modes (saturation). — [Hamel Husain FAQ](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html); [Alex Strick van Linschoten](https://alexstrick.com/posts/2025-05-23-error-analysis-to-find-failure-modes.html)

### Inferences
- A defensible acceptance rule implied by these sources: accept a harness change only if it improves the capability suite by more than the measured run-to-run spread across repeated runs, does not regress the near-100% regression suite, and does not blow up cost/latency metrics; ship behind an online A/B where possible.
- Harness configs (prompts, tool schemas, middleware, AGENTS.md/skills) are versioned as code in git, which makes rollback and per-model branches routine.

### Gaps
- No primary source found giving total dollar or engineer-week cost of a harness improvement campaign (e.g., LangChain's Terminal-Bench loop cost, number of iterations).
- No published explicit statistical stopping rules (e.g., required number of seeds) from labs beyond general noise warnings.
